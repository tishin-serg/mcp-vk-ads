# Ошибка unknown_source и безопасные примеры ретаргетинга

Проверено 2026-10-17: код main, официальная документация и только живые GET.
Ни одного POST/DELETE в этом исследовании. Примеры ниже не выполнялись.

## Диагноз и границы подтверждения

В отклонённом запросе object_type=segment и object_id обозначают вложенный
segment ID. Формат relations=[{object_type,object_id}] документирован:
вложенные сегменты в целом разрешены, циклы запрещены. Подмена object_id на ID
relation, counter source или manager cabinet ошибочна.

GET проблемного источника вернул flags=[subsegment,cross_device]. Это внутренний
узел составного сегмента; родитель имеет with_subsegments. Чтение такого узла
и его правил удалось в том же agency-client, который владеет им (users: master).
Таким образом, объяснение «сегмента вообще нет» неверно. Ответ POST, предоставленный
пользователем, означает, что VK не разрешил этот ID как источник данного создания.
Вероятная причина — повторное использование внутреннего subsegment. Публичная
документация не описывает правило его write-resolver; без нового POST или ответа
поддержки VK нельзя окончательно исключить другие ограничения этого источника.
Мы не воспроизводили отказ записью и не проверяли обходные write-маршруты.

Отдельная проблема payload: публичный Segment описывает pass_condition от 1 до
числа relations, как порог количества условий пользователя. 1 — хотя бы одно;
число relations — все условия. В старых внутренних отрицательных subsegment
GET действительно возвращает 0. Это наблюдение внутреннего представления,
а не документированный контракт POST для произвольного NOT. Нельзя приписывать
unknown_source именно нулю: VK сообщил ошибку разрешения источника, а не invalid_condition.

raw_request передаёт JSON без преобразования relations/object_id/pass_condition.
Дефект runtime MCP не обнаружен. Не нужны новый tool, автоматическая замена ID,
автоматическое разворачивание чужих сегментов или альтернативный транспорт.
Блокировка вызова OpenAI — отдельный слой; её не следует повторять другим каналом.

## Предложение: прямые источники счётчика

[Машиночитаемые примеры трёх вызовов](examples/retargeting-counter-segments.json).
Это шаблоны для review, не разрешение на выполнение: source_id=1234567 фиктивный.
Подставить проверенный Top@Mail counter source_id из params существующей relation,
не её object_id и не id связи из списка counters. goal_id — строка события,
например jse:addToCart/jse:purchase; не числовой ID цели из goals.json.

SegmentRelations показывает source_id; пример Segments использует counter_id.
В примерах выбран source_id по контракту общего объекта relation и фактическим
GET params. Принятие этих конкретных тел при POST ещё не проверено.

Пусть Cn — пользователи с хотя бы одним addToCart в накопительном окне left=n,
right=0; P — пользователи с purchase в согласованном окне. Тогда:

| Группа | Все условия AND | pass_condition |
|---|---|---|
| 0–3 | C3 AND NOT P | 2 |
| После 3 до 15 | C15 AND NOT C3 AND NOT P | 3 |
| После 15 до 30 | C30 AND NOT C15 AND NOT P | 3 |

Каждая строка — один новый сегмент с прямыми remarketing_counter relations.
У всех right=0, окна C3/C15/C30 используют один counter, одно событие и одинаковые
правила времени. type=negative исключает **пользователей, входящих в источник**,
а не удаляет отдельное событие из истории. Пользователь с корзинами во всех трёх
окнах должен попасть только в первую группу; покупка исключает его из всех трёх,
даже если покупка другого товара. Это не правило «не купил именно товар корзины».
Пустое значение purchase-event, другое имя события или иной источник меняют смысл.

30 дней покупок в шаблоне — пример, совпадающий с прочитанными именованными
аудиториями, а не согласованное бизнес-решение. «Без покупателей» требует выбора
периода. Найденная аудитория с названием «за всё время» фактически хранит 365 дней;
нельзя обещать исключение всех исторических покупателей по её названию.

Официальные границы: 0 <= right < left <= 365, единица — дни до запроса.
Справка не устанавливает включённость границ, календарное округление/таймзону.
Поэтому не обещаем точные часы и не заменяем right=3 на right=4 автоматически.
Разность накопительных множеств избегает самостоятельно придуманного промежутка
между 3 и 4 / 15 и 16 днями. «4–15/16–30» — бизнес-названия этих групп;
отображение на календарные дни ещё надо сверить в VK UI/с поддержкой.
Непересечение доказуемо на одном согласованном снимке множеств; задержки обновления
аудиторий и identity resolution VK не измерены этим GET-исследованием.

## Можно ли переиспользовать существующие аудитории

Именованные аудитории имеют правила корзины 0–3 / 4–15 / 16–30 и инверсию purchase
0–30. Все их внутренние узлы прочитаны отдельно. Первая логически соответствует
C3 AND NOT P30. Вторая и третья не исключают пользователей с более свежей корзиной:
один человек может входить сразу в несколько окон. Одного переиспользования этих
трёх ID недостаточно для требуемого непересечения. Первую можно рассмотреть для
новой группы при согласованном P30 и поддержке её выбранным package.

У существующих групп динамического ретаргетинга фактически другие источники —
remarketing_pricelist с negative_action=purchase. Этот параметр не доказывает
глобальное исключение пользователей-покупателей. Группы/сегменты не менялись.
Не подтверждены знак минус у targetings.segments и автоматическое AND списка
сегментов: не используем их как готовую замену исключающим правилам.

## Продолжение после согласования

1. Уточнить период исключения покупателей и трактовку границ дней.
2. Согласовать конкретные новые сегменты и payload. До этого — только GET.
3. При разрешённом write и отсутствии блокировки OpenAI: один явный raw POST
   на сегмент, затем GET сегмента и /relations.json. Не retry по network/5xx;
   сначала сверить результат GET. При unknown_source остановиться, не перебирать ID.
4. Проверить source_id/goal_id, positive/negative, окна и pass_condition в read-back.
   Создавать только новую blocked-структуру campaign/groups/banners по отдельному
   разрешению; прежние объекты не трогать. Динамический каталог и товарные связи
   проверять отдельно: статический smoke этого не доказывает.

## Проверки и первичные источники

Regression tests проверяют неизменность wire JSON, передачу HTTP 400 unknown_source
без retry/проверочного GET и логическое разбиение шаблонов на синтетических множествах.
Они не имитируют доказательство успешного создания в VK или календарные границы.
Локально: npm ci, typecheck, build, 142 теста (138 source + 4 dist, без пропусков),
runtime audit — 0 уязвимостей. Runtime-код и рабочий экземпляр MCP не менялись.

Прочитано с официального сайта по HTTPS (HTTP 200):

- [Segments](https://ads.vk.ru/en/doc/api/resource/Segments): вложение и ограничения, create body.
- [SegmentRelations](https://ads.vk.ru/en/doc/api/resource/SegmentRelations): relation body, params/source_id.
- [SegmentRelation](https://ads.vk.ru/en/doc/api/object/SegmentRelation): object_type/object_id/params.
- [Segment](https://ads.vk.ru/en/doc/api/object/Segment): порог pass_condition.
- [SegmentParams, RU](https://ads.vk.ru/ru/doc/api/info/SegmentParams): positive/negative, left/right.
- [Targetings](https://ads.vk.ru/en/doc/api/object/Targetings): поле segments; явной семантики отрицательных ID здесь нет.
